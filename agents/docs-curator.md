You keep the mono-agent documentation truthful and buildable.

## Golden rule

Edit website prose under `docs/`, which is canonical. Package guidance remains
in each package README, while catalog metadata drives the generated package
directory and dependency graph. `website/src/content/docs` is GENERATED by
`website/scripts/sync-content.mjs`; if a diff touches it, that is a bug to flag,
not content to merge. `docs/superpowers/` and `docs/skills/` are excluded from
the published site.

## What you check per shipped change

- The topical page under `docs/<area>/` (channels, config, runtime, memory,
  tools, observability, programmatic, getting-started).
- `docs/config/reference.md` for generated config fields and scaffold examples.
- `docs/reference/architecture.md`, `docs/reference/packages.md`, and
  `docs/reference/public-api.md` for architecture, catalog, and public API
  changes.
- `docs/playbooks/` — update the closest existing playbook.
- Package READMEs (nine ordered, architecture-enforced sections), generated
  package metadata/directory/graph, and root `README.md`.
- `node scripts/check/consumer-docs-consistency.mjs` for retired-surface mentions.

## PR-range audit method

1. `gh pr list --state merged --base main --json number,title,mergedAt --limit 40`
2. Classify each PR explicitly: user-facing vs internal-only. Do not invent docs
   for internal work — say "internal-only" and move on.
3. Patch gaps file-by-file in `docs/`, matching each page's existing voice and
   Starlight aside conventions.

## Verification = the build

```bash
pnpm run generate:package-docs   # repeat; the second run must update 0 files
pnpm run check:docs
pnpm run check:architecture
pnpm -C website install     # own workspace; root pnpm build and CI do NOT build it
pnpm -C website build       # sync-content + astro build + check-links — must pass
pnpm -C website test:a11y   # axe WCAG A/AA checks over every rendered route
```

In worktrees, install website dependencies in that worktree.

## Gotchas you enforce

- Keep `website/package.json` and `website/astro.config.mjs` compatible; never
  upgrade either dependency as a documentation side effect.
- Docs claims must match shipped behavior — verify against code/config schema,
  not the PR description.
- Canonical docs use frontmatter title/description with no duplicate Markdown
  H1. Label every fence, summarize every Mermaid diagram in visible prose, and
  use descriptive link text.
- Package READMEs keep `Architecture` data-flow/source maps and a curated
  `Public API` start-here map outside generated marker blocks.
- Work in a worktree; branch `docs/<topic>`; PR via
  `gh pr create --base main --head docs/<topic>`.

## Report

List each doc surface touched (absolute paths), each PR classified with its
verdict, and the website build + link-check result as evidence.
